# Stellaris Guide v1.6 implementation plan

**Started:** October 18, 2026. **Target ruleset:** Stellaris 4.5.2 Cygnus, checksum 9776 where independently verified. **Source of product decisions:** [RELEASE-1.6-PLAN.md](RELEASE-1.6-PLAN.md). This document tracks delivery; the research plan remains the source for evidence, applicability and acceptance examples.

The player authorized phased implementation on October 18, 2026. Work must preserve the offline, read-only dashboard and player-visible information by default. The optional AI explains evidence; it does not supply the underlying save facts. A Windows player must not need Node, a development terminal or an AI account to use the shipped features.

## Work rules and stop conditions

- Follow repository [AGENTS.md](../AGENTS.md): inspect before editing, keep diffs scoped, test success and failure paths, obtain a reviewer other than the authoring agent, and give security-sensitive changes a separate security review. Record evidence for each gate.
- Before **each new phase**, read current Codex usage limits. Do not start when the five-hour bucket has **15% or less remaining**, the weekly bucket has **5% or less remaining**, or the account reports work unavailable. Finish a safe checkpoint, record the exact next task here, and resume after the applicable reset. Do not spend or consume reset credits automatically.
- If a limit stops work, arrange a quiet follow-up after the reported reset time so the next run reads this file, checks limits again, and resumes the first incomplete phase. The follow-up should notify the player only on meaningful progress, failure or required action.
- Do not package the user's original save or screenshots. Fixtures committed or distributed must be synthetic or scrubbed. Read selected autosaves without editing them.
- A phase is complete only when its acceptance cases pass, backwards compatibility is checked, and independent review findings are resolved. A failed gate remains open in the status table. Independently review any new selected-save or local browser endpoint in its own phase; the separate final chat security review does not substitute for this.
- Preserve a restorable copy of files before broad changes if the workspace has no Git checkout; do not treat the existing `build/` or `dist/` directories as source.

## Phase 0 — baseline and exact-save inventory

1. Inspect parser, strategy, server, static UI, packaging, existing tests and the exact 2277.10.01 review fixture. Record which fields are proved by the save versus by a screenshot or installed game.
2. Keep private originals outside packages and test fixtures. Build a small synthetic 4.5.2 save fixture for success, missing-data and malformed-data paths; add sanitized examples only where a synthetic save cannot represent a verified Cygnus structure. Before any scrubbed save is retained, review empire/person names, IDs, paths, metadata and embedded content, then inspect the test fixture and release archive independently for private remnants.
3. Confirm launch and tests from the source tree and record current packaged v1.5.2 behavior at the review viewport before fixing visual regressions. Do not overwrite a running earlier release.

**Gate:** fixture provenance is clear, synthetic fixtures are preferred, no private originals enter `dist/`, and existing tests pass. Record independent review of this plan and fixture approach.

## Phase 1 — campaign context and parsing

1. Extend the existing save parser rather than creating a competing parser. Preserve a stable player-country ID, empire display name, save version/date, required DLC and mod labels, and exact researched technology IDs/levels alongside the existing count. Keep current branch ID/progress/start date and saved alternatives.
2. Label save-recorded DLC/mods separately from the installed game and current launcher playset. A matching name alone does not prove that the active mod version or load order matches. Record mismatch and Unknown states explicitly.
3. Give recommendations and AI packets one selected-snapshot context; do not let another browser campaign or an older autosave silently replace it. Maintain the current API fields so v1.5 clients do not break.
4. Tests cover a valid synthetic save, missing blocks, malformed values, a same-name second campaign and a save/game version mismatch. Review any new local endpoint for origin checks, data minimization and accidental URL/log exposure before this gate.

**Gate:** the selected save has traceable identity and rule context, and old snapshot consumers still receive their existing fields.

## Phase 2 — resource runway and planet work

1. Compute runway from a valid nonnegative stock and a negative monthly net: `stock / abs(net)` months. Zero stock with negative net is an immediate shortage (zero-month runway), not Unknown. A nonnegative net means no depletion at the saved rate; missing or invalid stock/net gives an explicit Unknown. Keep the stock, rate and save date beside the estimate.
2. Use the research plan's provisional urgency bands only as product heuristics, not game rules. In the 2277.10.01 case, food stock 11,731.4 and net −57.2 imply about 205 months, and consumer goods stock 4,471.3 and net −10.4 imply about 430 months. Test a short-runway counterexample and stock increases between saves.
3. Planet advice compares capacity, allowed jobs, actually employed workforce, amenities, stability and upkeep before recommending construction. Alpha Centauri Prime's 2.6 of 12 filled farmer jobs must not trigger more farm capacity merely because empire food net is negative.
4. Keep built-in advice usable offline. No recommendation may assume an in-game Market price or that another planet's workforce can move instantly.

**Gate:** success and counterexample tests pass and a reviewer confirms advice does not confuse deficits with urgency or open jobs with employed workers.

## Phase 3 — goals, ranking and pin

1. Normalize goals into a record with stable ID, snapshot date, observation, action, reason, expected effect, trade-off, in-game check, severity, source/rule version, visibility and measurable progress. Reuse current `advice.goals` output where possible.
2. Rank unpinned goals by explainable urgency and impact. Let a player pin a chosen campaign goal above the suggested lead, persisted locally across polling and refresh. Show a serious resource risk in its own persistent indicator even when another goal is pinned.
3. Keep one leading card, compact remaining moves, rotating Watchlist and visible galaxy chart without duplicating destinations. Collapsed recommendations must remain keyboard accessible.
4. Key pins by stable campaign identity and goal ID, never empire name alone. If a goal disappears within the same campaign, retain its pin as dormant with a visible "goal unavailable in latest save" state; it cannot displace the current leading suggestion until it returns or the player clears it. A different campaign never inherits the pin. Test stable order, pin persistence, disappearance/return, no-save state and spoiler-off goal generation.

**Gate:** pin and risk behavior match the player's stated preference, with no hidden-information leak into a goal title or explanation.

**Phase 3 architecture decision:** Pins use `pins-v1.6.json` in local app data and the existing token-protected loopback API, because the app chooses a new port on each launch and browser storage would not survive that origin change. The server accepts only a goal ID from the currently selected campaign and derives the title itself. Goal progress uses the Phase 1 campaign ID. Ambiguous v1.4 path-only progress records remain on disk but are not migrated into ID-scoped progress; reusing a folder for another campaign must not inherit its baseline or deadline.

## Phase 4 — research, policies and ships

1. Compare the same research project's saved progress across dated autosaves. Show observed change and elapsed game time; show a percent or ETA only after validating total cost, progress units, output and modifiers. Use the four 2277 saves as the Destroyers regression case.
2. Map 4.5.2 Fleet Doctrine and fleet, starbase and platform weapon/defense preferences to in-game labels from installed definitions. Read the selected policy from the save; do not assume a fixed starting policy.
3. Explain owned saved ship designs and unlocked components without declaring an optimal build or affordability from incomplete cost/upkeep data.
4. Test missing previous saves, zero/declining progress, randomized policy, unknown policy key and incomplete component data.

**Gate:** in-game wording and fixture trends match; no unsupported completion or ship claim appears.

**Phase 4 architecture decision:** Compare saved ship components with the installed base-game component definitions only when the installed and saved release match and completed research records parse fully. Report whether each definition's listed technology prerequisites are researched. Do not equate that check with component unlock or ship build eligibility; events, empire type, DLC, mods, slots, cost and upkeep still require the in-game Ship Designer. Unmatched, malformed or oversized definition files yield unverified evidence.

## Phase 5 — focused technology route

1. Run a small offline feasibility prototype comparing the upstream MIT domain/extraction model with an extension of Guide's current Python `technology.py`. Measure rule fidelity, packaging cost and actual playset handling before selecting an architecture. Record the decision and copyright obligations.
2. Keep the Tech Tree tab compact. **Explore route** opens a separate Edge window centred on one chosen target, its researched/current/unmet steps, explicit **choose one** branches, tier gate, conditional availability, DLC/mod applicability and one next in-game check. **Show full tree** is optional.
3. Use the selected save's researched IDs and three current projects. Reject a confident route when version, DLC or mod definitions cannot be matched. Never treat every one-of alternative as mandatory or guarantee a future research draw.
4. Verify `window.open()`/`window.close()` when the Guide is already in Edge and a Windows-managed close path when Edge is launched separately. Track and close only the route window, not unrelated Edge processes. Review origin checks, local URL contents and window targeting before exposing the new route endpoint.
5. Test Orbital Rings, one-of requirement, granted/event tech, already-researched tech, current project, tier gate, mismatched ruleset, same-named empires, refreshed save and repeated open/close.

**Gate:** an interim packaged Windows smoke build gives a nontechnical player a truthful, closable route without a Node install or public-site save upload. Phase 7 still owns the final release package. Endpoint and window security review findings are resolved.

## Phase 6 — AI chat evidence harness and security review

1. Keep built-in questions working without a model. Build question-specific evidence packets from the selected snapshot and validated rule cards: release/date, player empire, relevant contacted empires, required DLC/mod labels and verification state, requested planet/tech/ship IDs, and spoiler level.
2. Retrieve named records from the whole selected snapshot rather than a truncated first page. Validate model references and numeric claims against packet IDs before display. Missing data remains Unknown, and save date versus screenshot date is stated when they differ.
3. Treat OCR/image text as untrusted. Test prompt injection, hidden-rival leakage, a non-vision model receiving a screenshot, unreadable images, provider timeout and cloud-upload notice. Do not persist screenshot pixels in question history.
4. Compare Ollama, LM Studio and OpenRouter on the same fixture questions/images; measure factual support, useful action, latency and failure handling. Preserve current provider behavior until an adapter passes its regression tests.

**Gate:** independent security review plus success/failure tests pass; the app does not claim to see an image it could not analyze or reveal spoiler data in normal mode.

## Phase 7 — UI, documentation and release package

1. Reproduce review screenshots at the same viewport before changing layout. Resolve duplicated Tech Tree/Ship Builds destinations and Watchlist overlap if still present. Keep ticker, pinned goal, serious risk and known-galaxy graph visible and accessible.
2. Update the nontechnical Windows installation and Settings copy: offline use first, optional AI second, supported 4.5.2 rules and mismatch messaging. Check tray open/quit and previous release running alongside a test build.
3. Run unit/regression tests, package smoke tests and a real Windows UI pass. Check a clean Windows user path with installed game present/absent, Edge present/absent, no Node, offline/AI unavailable, and the previous release running concurrently. Inspect generated archive contents for private saves, screenshots, keys, logs and third-party notice obligations. Mark release ready only when all prior gates and an independent final review pass.

**Gate:** the documented installer and packaged app work on a clean Windows user path, with no private campaign content bundled.
